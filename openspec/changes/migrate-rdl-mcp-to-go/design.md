# Design

## Context

Див. `proposal.md` і обидві delta specs. Наявний `rdl_mcp/server.py` реєструє 15 tools і сам обробляє JSON-RPC по stdio; `reader.py`, `columns.py`, `datasets.py`, `parameters.py`, `validation.py` і `xml_utils.py` реалізують поведінку. Python-тести перевіряють переважно методи класу, тому до перенесення треба зафіксувати також справжні MCP-відповіді. `server.json` і release workflows прив'язані до PyPI.

## Goals / Non-Goals

**Goals:**

- Одна нативна Go-програма для MCP transport і всіх RDL-операцій, збереження зовнішніх tool-контрактів.
- Порівняння Python та Go на спільних файлах і викликах перед видаленням Python-пакета.
- Публікація бінарників і коректне представлення Go-пакета у MCP Registry після перевірки схеми.

**Non-Goals:**

- HTTP transport, нові tools, підтримка Matrix/Chart, зміна бізнес-правил редагування RDL.
- Побайтово однакове форматування XML або JSON, якщо зберігається їхня змістова структура й документ читається SSRS.

## Decisions

### MCP transport та залежності

Використати `github.com/modelcontextprotocol/go-sdk/mcp` версії `v1.8.0`: `mcp.Server`, `mcp.StdioTransport`, `mcp.AddTool` і типізовані аргументи. SDK виконує MCP handshake, валідацію аргументів та серіалізацію повідомлень; окремий JSON-RPC transport не підтримувати. Альтернатива — перенести власний Python transport у Go — зберегла б історичні деталі помилок, але збільшила б код і відповідальність за протокол. Погоджену пряму залежність `regexp2` описано нижче; інші прямі Go-залежності потребують окремого аппруву користувача. Транзитивні залежності SDK перевірити й зафіксувати через `go.sum`.

SDK може інакше формувати JSON-RPC помилки й handshake; сумісність визначати на рівні підтримуваного MCP-клієнта, каталогів tools та змісту успішних результатів, а не байтів усієї відповіді. Існуючі бізнес-відмови `success=false` лишаються в JSON результату; виняткові помилки вводу/IO віддаються як помилки виклику за правилами SDK.

За окремим рішенням користувача прийнято поведінку SDK `v1.8.0` для невалідного JSON у stdio: помилка декодування завершує сеанс, і клієнт запускає процес знову. Невідомий метод, невалідні аргументи окремого tool та інші коректно сформовані запити SHALL не заважати наступному виклику. Інтеграційний тест перевіряє ці два випадки окремо.

Для `field_pattern` користувач окремо погодив `github.com/dlclark/regexp2/v2@v2.8.0`. Python `re` приймає lookbehind, який Go `regexp` не підтримує; Go-реалізація перетворює Python-синтаксис іменованих груп і посилань на них перед компіляцією, зберігаючи Unicode-поведінку `regexp2`. Паритет перевіряти диференційними fixtures; неперевірені відмінності синтаксису не вважати автоматично сумісними.

### Go структура й XML

Один `cmd/rdl-mcp` запускає сервер; внутрішні пакети розділяють MCP-адаптер, читання/запис XML та операції зі звітами. Публічного Go API поки немає: реалізація в `internal/`. XML обробляти стандартним `encoding/xml`, з явним збереженням невідомих елементів, атрибутів, просторів імен та порядку, які не змінює tool. Альтернатива — зовнішня DOM-бібліотека — не обґрунтована, поки стандартна бібліотека проходить паритетні тести; якщо не проходить, підготувати конкретний приклад втрати даних і запросити аппрув до додавання бібліотеки.

SDK може виконувати tool handlers паралельно. Для передбачуваного читання і запису одного RDL процес серіалізує операції над файлами; оптимізувати гранулярність блокування лише за виміряної потреби. Перед записом обробити документ у пам'яті й перевірити результат; нецільові елементи SHALL лишатися змістово незмінними. Не проголошувати побайтовий паритет форматування.

### Доказ паритету

Спочатку виконати Python тести й зняти санітизовані baseline fixtures через реальний stdio-сервер: `initialize`, `tools/list`, всі 15 `tools/call`, значення за замовчуванням, помилки, послідовність викликів. Для записів використовувати окремі копії RDL, порівнювати JSON результати та XML-дерево після змін. Додати Go unit тести для XML і операцій та інтеграційний тест через MCP SDK-клієнт і pipe/EOF. JSON порівнювати структурно; XML — за елементами, атрибутами, текстом і збереженням невідомого вмісту. Будь-яку прийняту різницю задокументувати окремо.

### Дистрибуція

Go-бінарники збирати для підтримуваних OS/архітектур і розміщувати в GitHub Releases; README показує запуск локального виконуваного файла через stdio. У поточному MCP Registry немає підтвердженої підтримки `registryType: go`; для registry обрати підтримуваний формат MCPB з `server.type: binary`, release URL та SHA-256 у `server.json`. Формувати MCPB лише після перевірки manifest/schema й запуску пакета в цільових клієнтах; утиліту пакування, якщо вона потребуватиме нової залежності проєкту, додати тільки після окремого аппруву. Альтернативи: OCI вимагає контейнерного доступу до локальних RDL, а PyPI-обгортка лишає Python у шляху запуску.

## Risks / Trade-offs

- Відмінності `encoding/xml` у префіксах, пробілах та порядку атрибутів → порівнювати XML семантично й перевірити збереження складних просторів імен; якщо втрачаються дані, зупинити цей зріз і погодити додаткову бібліотеку.
- SDK змінює схеми tools або перетворення `nil`/порожніх значень → порівняти повний каталог і JSON результати з Python baseline; для необов'язкових полів використовувати вказівники/явні default-и.
- Пакет MCPB або запис registry може не працювати в частини клієнтів → перевірити на тестовому release artifact і лишити документований запуск бінарника напряму.
- Вилучення PyPI-дистрибуції порушить стару команду `uvx rdl-mcp` → явно оголосити breaking change і залишити попередній PyPI release доступним для повернення, доки Go-реліз не перевірений.

## Migration Plan

1. Зафіксувати Python baseline й додати інтеграційні fixtures без зміни продуктового коду.
2. Перенести RDL-операції невеликими зрізами, постійно порівнюючи Python та Go на однакових файлах.
3. Під'єднати MCP SDK, перевірити всі tools, stdio, помилки, EOF, і запустити `go build ./...`, `go vet ./...`, `go test -race ./...`.
4. Підготувати Go release artifacts, MCPB та новий `server.json`; перевірити schema, цільові клієнти і шлях встановлення до зміни публікації.
5. Прибрати Python реалізацію й PyPI workflow, оновити README/CLAUDE.md та опублікувати Go-реліз після окремого рішення про публікацію. Для rollback використати попередній тег/PyPI пакет і повернути клієнтську команду `uvx rdl-mcp`; не видаляти його з PyPI.
